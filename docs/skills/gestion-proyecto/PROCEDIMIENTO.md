# Procedimiento compartido de gestión del proyecto

Autoridad: [Reglas compartidas](../../REGLAS_COMPARTIDAS.md). Usa [Router](../../colaboracion/ROUTER_CONTEXTO.md), [Flujo](../../colaboracion/FLUJO_TRABAJO.md) y los índices de objetivos, módulos, decisiones y pendientes. Es un procedimiento manual.

Para recibir instrucciones académicas o técnicas, registrar una tarea y continuarla desde otro asistente, aplica el subprocedimiento [Recepción, documentación y seguimiento de tareas](RECEPCION_TAREAS.md). Allí se definen acceso al original, transcripción fiel, identificadores, estados de actividad y evidencia; este documento conserva las reglas generales de gestión. No constituye otra Skill ni un sistema adicional de sesiones.

## Actualización basada en evidencia

1. Comprueba rama, cambios previos y permiso para editar documentación o gestionar recursos remotos.
2. Lee objetivos y acuerdos existentes. No inventes requisitos, integrantes, fechas de entrega ni distribución de responsabilidades. Si faltan, conserva «pendiente de acordar».
3. Para cada tarea identifica objetivo, responsable conocido, dependencia, estado, criterio de aceptación, evidencia y siguiente acción. Una nota redactada no implica que su contenido haya sido implementado o probado.
4. Usa estados comprensibles: propuesto, acordado, en curso, bloqueado, en revisión y completado. Completar requiere evidencia de los criterios; bloquear requiere describir una dependencia concreta.
5. Actualiza Dashboard e índices solo cuando cambie información relevante. Conserva enlaces e historia; coordina archivos compartidos. Registra cambios relevantes mediante [Bitácora](../bitacora/PROCEDIMIENTO.md).

No estimes porcentajes de avance. Puedes presentar un conteo de criterios verificados si el conjunto está definido, mostrando cuáles y la evidencia. No mezcles cumplimiento documental con avance de implementación del detector.

## Fuentes y distribución

Obsidian conserva contexto duradero, arquitectura aprobada, decisiones, investigación y bitácoras. Issues organizan trabajo accionable; PR documentan revisión del cambio concreto. Cuando existan referencias verificadas, enlázalas en vez de duplicar discusiones o mantener dos estados independientes. Sin acceso remoto autorizado, marca esas acciones pendientes.

Las recomendaciones de ramas y revisión no prueban protección técnica de main. No hagas git add, commit, push, merge ni modificaciones a main sin autorización explícita. En simulación/solo lectura con escritura prohibida, presenta el estado propuesto sin persistirlo.
